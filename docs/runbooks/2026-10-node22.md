# Node 22 switch (handoff step 7, delivery-order-app #554)

The box moves from per-user nvm Node 20 to one system Node 22 (NodeSource apt, role `nodejs`), **one Environment
at a time**: staging now with `release/v1.4.0`, production once v1.4.0 is merged into `main`.

## Why the split works

Each Environment picks its Node independently, so the two can run side by side:

| | Production (until v1.4.0 is merged) | Staging (now) |
|---|---|---|
| `tenants` entry | `nvm_node_version: v20.19.5` | no `nvm_node_version` |
| PM2 unit | `~/.nvm/versions/node/v20.19.5/…/pm2` (unchanged, `--check` = ok) | `/usr/lib/node_modules/pm2/bin/pm2` |
| `~/.nvm` | kept: `deploy-server.sh` sources it, so `node`/`pm2` = Node 20 | renamed `~/.nvm.retired` by the `tenant` role, so `deploy-server.sh` falls through to `/usr/bin/node` |
| App process | `bash -c 'npm run start'`, `npm` from the dump's PATH = nvm | same, nvm dir gone, `npm` resolves to `/usr/bin/npm` (Node 22) |
| Deploys | **none until merged** (see below) | `workflow_dispatch` on `release/v1.4.0` (builds with Node 22) |

The PM2 dumps store `PATH` with the nvm bin dir first (seen 2026-10-01). That is why `~/.nvm` must move: while it
exists, a `pm2 restart` brings back Node 20 whatever the unit says.

**Production guard (by convention, nothing enforces it):** do not push a `peperoncini/production/v*` tag on a v1.4.0
commit before production is switched: the runner builds with Node 22 and `deploy-server.sh` would run it under nvm 20.
Note also that `main`'s old `deploy.yml` cannot deploy production any more since step 6 (it rsyncs with
`--chown=:peperoncini-www`, a group that no longer exists, and pulls `.env.*` to the runner), so until the merge there is
no production deploy path at all, not even a hotfix.

## Phase A: staging (now)

1. Dry run, then apply (owner):

   ```sh
   ansible-playbook site.yml --check --diff --tags nodejs,tenant < /dev/null > check.log 2>&1
   ansible-playbook site.yml --tags nodejs,tenant < /dev/null > apply.log 2>&1
   ```

   Expected `--check`: the 4 NodeSource files, `nodejs=22.*` and PM2 *failing* (ignored: no NodeSource source yet in a
   dry run), staging `.nvm` retired, staging PM2 unit diff. Production lines all `ok`. Nothing is restarted.

2. Verify the install:

   ```sh
   ssh IncServer 'node -v; npm -v; pm2 -v; apt-cache policy nodejs | head -3'   # v22.x, pm2 6.0.11, nodesource
   ssh IncServer 'sudo unattended-upgrade --dry-run -d 2>&1 | grep -i "allowed origins"'   # lists site=deb.nodesource.com
   ```

3. Restart staging onto Node 22 (staging only, any time):

   ```sh
   ssh IncServer 'sudo -n bash -s' <<'EOF'
   systemctl restart pm2-peperoncini-staging
   sleep 5
   for u in peperoncini peperoncini-staging; do   # staging /usr/bin/node, production .nvm/…/v20.19.5
     for p in $(pgrep -u "$u" -f 'blitz start'); do echo "$u: $(readlink /proc/$p/exe)"; done | grep -v dash
   done
   EOF
   curl -sS -o /dev/null -w '%{http_code}\n' https://staging.pizzeria-peperoncini.ch/   # 200 after the cold start (~60 s)
   ```

   This runs staging's *current* build (made with Node 20) on Node 22: a rehearsal of production's restart before
   its deploy.

4. Staging deploy, the first run of the #553 pipeline:

   ```sh
   gh workflow run deploy.yml --repo kuuak/delivery-order-app --ref release/v1.4.0 -f client=peperoncini -f environment=staging
   gh run watch --repo kuuak/delivery-order-app
   ```

   2026-10-01: CI green, but staging crash-looped on `Cannot find module './logs/internal.js'` (`@sentry/core`):
   `scripts/deploy-rsync-exclude` drops every `logs`/`test`/`docs` dir inside `node_modules` (delivery-order-app #564).
   Redeploy after #564 lands. Done (run 36838774275): 200, `/usr/bin/node`, PM2 stable, `127.0.0.1:3010`.

5. Smoke test staging (by hand, in a browser, on https://staging.pizzeria-peperoncini.ch):
   - **Login**: customer account and admin.
   - **Checkout**: place an order end to end (mail lands in Mailpit, ADR-0003: nothing leaves the box).
   - **Push notification**: the order reaches the admin / dashboard with its push notification.
   - **Cash register**: open it, create and park an order, load it back.
   - **Cron**: `curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://staging.pizzeria-peperoncini.ch/api/cron/purge-expired-tokens`
     → 200 (without the header → 401, checked). Take `CRON_SECRET` from staging's env files yourself; never paste it into
     an agent session. `check-pending-payments` only matters for SumUp Tenants (none today), skip it.
   - **Error reporting**: browser path to GlitchTip already checked 2026-10-01.
   - Already checked 2026-10-01: `/usr/bin/node`, PM2 stable, bound to `127.0.0.1:3010` (#558).

   All green → phase A is done; record it in the handoff and the cleanup runbook's table.

   Done 2026-10-03. Found: Wallee rejects attribute keys over 40 chars (#571, also on production), plus one more app bug.

**Rollback (staging):** put `nvm_node_version: v20.19.5` back on the staging entry, then
`mv -T ~/.nvm.retired ~/.nvm` as `peperoncini-staging`, apply `--tags tenant`, `systemctl restart pm2-peperoncini-staging`.
Only useful for a pre-v1.4.0 build: v1.4.0 itself requires Node 22.

## Phase B: production (after v1.4.0 is merged into `main`, closed-pizzeria window)

1. Delete the `nvm_node_version` line (and its comment) from the production entry in `group_vars/all/vars.yml`.
2. `--check --diff --tags tenant` must show only: production `.nvm` retired, production PM2 unit diff. Apply.
3. `systemctl restart pm2-peperoncini`; same `readlink` check (`/usr/bin/node`), 200 on www after ~60 s.
4. Push the `peperoncini/production/v1.4.0` tag (or whatever the release tag is); watch the run; same smoke test as
   staging, on production.

**Rollback (production):** before the deploy, the same as staging. After the v1.4.0 deploy there is no going back to
Node 20: roll back the app (`_old/`) only together with the nvm rollback.

## Afterwards

- Delete `~/.nvm.retired` in both homes after a week of quiet (step 9 housekeeping).
- With no Environment left on nvm, drop the `nvm_node_version` branch from `roles/tenant/templates/pm2.service.j2`
  and the `.bashrc` nvm lines (harmless once `.nvm` is gone).
- delivery-order-app #557: provisioning scripts and the `refresh-staging` README still assume per-user nvm.
